# 三人分工与阶段计划

日期：2026-10-01。状态：基于当前进度制定的建议分工，可直接作为首次团队讨论与任务领取依据。

## 1. 结论及前提

推荐：**A（你）负责 VFS 主线、原生后端和集成；B 负责 ext2、FAT32；C 负责 HAL、块设备和 LoongArch。** 每个人同时负责自己模块的测试、说明与演示。

理由：你已经掌握项目历史并开始最小 VFS，继续这条主线可以减少重新交接成本；ext2 与 FAT32 面向同一套接口，交由同一人先后实现便于复用经验；平台相关工作集中管理，避免两个人分别修改启动、中断和磁盘驱动。

这不是等量分工。C 的架构移植不确定性最大，B 连续实现两种格式也很重；A 的公共接口和集成同样是实质开发。三人都从零学习、投入时间未知，目前无法承诺在预计结题前完整交付双平台三文件系统。需要用早期实测调整任务，不能用平均文件数衡量公平。

本分工不把某个人安排为专职“测试/写报告”。各模块都需要实现与验证，由 A 汇总最终材料，B/C 提供各自章节及证据。

### 为什么不采用其他常见分法

| 分法 | 问题或适用条件 |
|---|---|
| 一人 xv6、一人 ext2、一人 FAT32 | 无人明确负责 HAL/LoongArch；容易各自写一套路径、挂载和驱动 |
| 一人开发、一人测试、一人文档 | 无法形成三条功能开发线，核心开发仍集中在一个人 |
| 一人 RISC-V、一人 LoongArch、一人 VFS | 两套平台版本容易复制文件系统与系统调用，最终难以合并 |
| 本方案：公共层／文件系统后端／平台层 | 接口数量较少、可各自自测；需要早期共享接口并控制公共文件冲突 |

最终目标仍为原生、ext2、FAT32 经同一 VFS 工作，并支持 RISC-V 与 LoongArch；课程范围如要缩减需另行确认，不能将阶段原型称为题目全部完成。

## 2. 三人的任务边界

| 人员 | 主责 | 交付物 | 明确不自行改动的内容 |
|---|---|---|---|
| A：你 | VFS 对象、引用、路径、挂载；原生 xv6 适配；文件系统相关系统调用、exec/cwd；公共接口与集成 | 最小 VFS 回归、挂载与系统调用、共享头文件、集成版本及总测试矩阵 | 不顺手重写平台寄存器/驱动，不替 B 实现磁盘格式算法 |
| B：文件系统负责人 | ext2 先行、FAT32 后续；格式识别、目录、数据映射、分配回收、创建/读写/截断；镜像与模块测试 | 两套后端、镜像参数与生成说明、支持范围、读写及持久化证据 | 不另写通用路径解析、mount 系统调用、磁盘驱动或私有用户 API |
| C：平台负责人 | 块设备接口、多磁盘；RISC-V HAL 整理；LoongArch 工具链、启动、异常、页表、切换、设备和用户态 | 双架构构建入口、平台代码、设备映射表、启动与双平台测试证据 | 不按平台复制 VFS/ext2/FAT32，不改变文件操作语义 |

### A：沿用现有进度继续最小 VFS

依次完成：

1. 核对 Ubuntu 已有 `vfs.h` 与第二步补丁的接口一致性。由用户自行检查、应用补丁并编译；本分工文件不是已执行记录。
2. 接入 vnode 初始化及原生普通文件读取、属性、释放，检查引用和锁。
3. 接入写入、创建、截断、目录修改，再迁移 exec 与 cwd；每次改动保持可编译、能说明失败清理。
4. 完成原生最小 VFS 回归，再提供挂载、通用目录列举及后端注册入口。
5. 接入 B 的 ext2/FAT32 和 C 的块设备实现；汇总两个平台上的统一结果。

独立验收：RISC-V 上原生根盘经 VFS 启动 `/init` 和 shell；打开、读写、dup/fork、删除后继续访问、exec、管道及设备行为正常；完整 usertests 保留真实记录。

### B：先完成一个后端的完整链路，再做另一个

依次完成：

1. 学会区分“文件偏移、文件系统块号、设备字节偏移”；与 A/C 核对共享接口。
2. 固定 ext2 镜像配置，读取超级块、根目录和已知文件；错误格式/不支持特性明确拒绝。
3. 实现创建、写入、截断及必要资源回收，覆盖跨块、较短覆盖、空间不足；再接入指定复制测试。
4. 用相同 VFS/块设备接口实现 FAT32。先完成声明范围内的名称与簇链操作，再逐项扩大范围。
5. 提供两种后端的边界清单、镜像重建说明与正常写回后的重启检查。

独立验收：在宿主测试中以普通镜像文件代替块设备，验证同一份格式解析/分配核心代码；随后必须在 xv6 中通过真实 VFS 和驱动验证。不能以 Ubuntu 挂载镜像成功替代自己后端成功。

宿主测试仅增加薄适配：文件读写模拟 `blk_read/blk_write`，必要的锁/内存/复制辅助仅用于测试。不要另写一份算法“模拟”内核实现，也不为此建设通用框架。并发和用户地址检查必须在内核验证。

### C：先交付能供别人使用的磁盘接口，同时尽早探查第二平台

依次完成：

1. 理解现有 VirtIO 单盘驱动、缓冲缓存与设备编号；先实现 RISC-V 多设备的读取验证及块设备契约。
2. 在独立分支开展 LoongArch 最小启动实验，尽早明确编译、加载方式、内存布局、串口和设备路径，形成证据或阻塞报告。不要等 VFS 完成再开始。
3. 逐步整理平台边界，保持 RISC-V 可运行。LoongArch 按“启动输出 → 异常/时钟 → 内存和上下文切换 → 用户态/系统调用 → 磁盘和 shell → 完整回归”推进。
4. 让两平台提供同一块设备/通用内核服务接口，最后运行同一份 VFS 和文件系统代码。

独立验收：RISC-V 上三份一次性测试镜像的设备隔离与跨扇区读取；LoongArch 每一层分别提供最小可运行证据。模拟器能启动、裸机能打印字符都不能称为 xv6 已移植完成。

LoongArch 的启动及设备接入需按实际 QEMU 版本确认。官方 `virt` 文档展示 PCI/PCIe 等平台设施，不能直接照搬 RISC-V 的固定 MMIO 地址及启动参数。[QEMU 官方平台说明](https://www.qemu.org/docs/master/system/loongarch/virt.html)。本机此前验证的是 QEMU 8.2.2；在线文档版本更新，不代表本机功能已验证。

## 3. 哪些工作真正可以独立进行

| 任务 | 不必等待什么 | 开始前必须共享什么 | 首次接入 |
|---|---|---|---|
| A 的原生最小 VFS | 不必等待 ext2、FAT32、LoongArch | 当前读取接口及原版行为 | 当前 Ubuntu RISC-V 原生根盘 |
| B 的 ext2 格式读取与写入核心 | 不必等待 A 完成路径/挂载，或 C 完成 LoongArch | 节点/返回值约定、块设备字节接口、镜像配置 | A 的 VFS + C 的 RISC-V 多盘 |
| C 的设备适配与 LoongArch 启动 | 不必等待两个新增文件系统 | 块接口、共用文件归属、构建参数职责 | 原生 xv6 + 公共 VFS 主线 |
| FAT32 | 可在 ext2 后端稳定后沿用同一接口 | 名称、节点身份、目录列举约定 | 已验证的多文件系统主线 |

独立开发指“主要修改自己的模块，依靠固定接口连接”，不等于“不沟通、不共享提交、不做中途验证”。首次只读对接只需识别挂载类型、查找预置文件并读出完整内容；不需要等所有写操作完成。

## 4. 面向零基础的起步安排

共同先学：C 的指针、结构体、函数指针；编译与链接；Git 提交和分支；内核/用户态；锁与引用计数。每个概念结合一段现有 xv6 代码解释，不要求先通读整本操作系统教材。

| 人员 | 第一项可交付的小任务 | 学习抓手 | 能回答才算理解 |
|---|---|---|---|
| A | 画出一次 open/read/close 和最后引用释放路径，核对现有读取接口 | `file.c`、`sysfile.c`、第二步补丁 | 为什么 dup 共用偏移？为什么 close 可能写磁盘？ |
| B | 从固定 ext2 镜像读出格式信息和一个已知文件 | 镜像布局、块接口、边界检查 | 这个字节偏移从哪里算出？文件跨块如何读取？ |
| C | 解释原单盘请求路径，读出第二设备的已知标记；并记录 LoongArch 启动探查结果 | `bio.c`、`virtio_disk.c`、启动/串口 | dev 是否真的选中了不同磁盘？CPU 执行入口在哪里？ |

第一轮每人交付“小成果 + 原始输出 + 不懂的问题”，不要让任何一人先包办通用框架或要求三人同时学习所有子系统。

### 不均衡时如何调整

- C 遇到阻塞后，应给出最小复现、预期/实际结果和涉及层次。下一次协作时共同定位，避免独自长时间尝试大面积修改。
- A 在原生 VFS 里程碑后，协助系统调用参数/返回值适配、exec 与 cwd 在第二平台的接入测试；不让 C 再复制一份文件系统逻辑。
- B 在 ext2 可接入后，负责跨平台镜像、文件内容检查和失败复现，分担 C 的验证工作；FAT32 仍由 B 主责。
- 若 10 月 7 日仍无 LoongArch 启动路径或 ext2 首次读取证据，立即评估资源与阶段展示，不等结题前再讨论。保留 FAT32/LoongArch 最终目标，必要的课程范围变化另行向教师确认。
- 后续记录实际投入、完成的小里程碑与阻塞，再调整工作量。现在不编造人日估算或三人的能力差异。

## 6. 文件归属与重叠区域

所有源码路径均相对 `~/AdvancedOS/xv6-riscv`，下面是规划归属，不表示文件已经新增或迁移。

| 文件/区域 | 主责与规则 |
|---|---|
| `kernel/vfs.h`、`vfs_backend.h`、`vfs.c`、`vfs_xv6.c` | A 管理公共接口及原生适配；B 提接口需求，不在私有分支擅自形成第二版定义 |
| `kernel/ext2.c/.h`、`fat32.c/.h` 及其必要拆分 | B；优先平铺少量文件，不先建设复杂目录框架 |
| 计划的 `kernel/blkdev.h/.c`、平台头文件和平台实现 | C；块接口调整须同时通知 A/B |
| `kernel/file.h/.c`、`sysfile.c`、文件系统系统调用与用户工具 | A；C 仅提交必要的平台接入修改 |
| `kernel/proc.h/.c`、`exec.c`、`main.c`、`defs.h` | A 负责合并；cwd/VFS 由 A，寄存器/上下文/启动差异由 C，按字段和函数协调 |
| `kernel/bio.c`、`buf.h`、`virtio_disk.c`、中断分发 | C 主责；改缓冲缓存或日志相关行为需 A 复核，防止影响原生文件系统 |
| `Makefile`、架构选择、链接脚本 | C 设计双架构选择，A 统一合并；B 只提供所需对象/测试清单 |
| 后端镜像生成和测试 | B；原生 VFS 测试 A；平台和块设备测试 C；集成清单 A 汇总 |

公共文件允许两个人提交小改动，但须先说明函数/字段范围；不要同时整体替换文件或大规模搬目录。
