## 2. 四次必须安排的接入

### G0：共同接口可用

负责人：A 汇总，B/C 核对。

- [ ] 三人拿到同一个公共开发提交号和 S0/D1 头文件版本。
- [ ] 说清每个返回节点是谁释放、是否带锁、能否睡眠、是否需要事务。
- [ ] 块接口明确 dev、字节单位、返回值、缓冲区来源、容量和非对齐行为。
- [ ] 固定第一份 ext2 镜像配置与原始内容，记录预期字节。
- [ ] C 列出公共文件修改范围和 LoongArch 启动探查结果。

判定：能用同一份声明编译各自相关代码或最小适配；如果依赖尚未实现，明确使用何种测试替身。只有签名讨论或语法检查不等于内核功能通过。

### G1：最小真实读取

负责人：A 组织，B 查后端，C 查设备。

- [ ] A 的 VFS 能接入原生根目录；本轮改动相关回归通过。
- [ ] C 的真实多盘驱动能区分原生与 ext2 设备，读取各自已知内容。
- [ ] B 的 ext2 从真实设备识别格式、找到预置文件，A 通过 VFS 读取完整内容。
- [ ] 在内核调试输出或只读诊断中证实 `/mnt` 的格式、实例、设备；不只检查路径存在。
- [ ] 失败后无半成品挂载、引用泄漏、根盘误写。

判定：这才是首次端到端接入。只读成功是一个有价值的里程碑，但还不满足创建、写入和截断需求。

### G2：可写后端与三文件系统

负责人：B 提供功能，A/C 配合定位。

- [ ] 先使 xv6↔ext2 双向复制成功，包含创建、跨块读写、较短内容截断与完整比较。
- [ ] 执行指定 VFS 测例，保留原始版本和测试版本标识，逐项检查实际输出。
- [ ] 按相同接口接 FAT32，三种文件系统在同一次运行中并存。
- [ ] 六个有向组合：xv6→ext2、ext2→xv6、xv6→FAT32、FAT32→xv6、ext2→FAT32、FAT32→ext2，全部比较长度和字节。
- [ ] 正常 sync/flush 完成后，用同一份未重建数据镜像重启，再读取比较；记录 QEMU 缓存设置与刷盘支持范围。

指定 `test1` 涉及创建/截断和跨路径复制；`test2` 展示的回读不能替代全文件校验，其主函数也没有传递内部测试失败作为最终返回值。因此本项目要求额外判定和完整比较，不仅看进程退出或结束提示。[指定 test1](https://github.com/yanjun-wen/xv6-extend-vfs/blob/main/tests/test1.c)、[指定 test2](https://github.com/yanjun-wen/xv6-extend-vfs/blob/main/tests/test2.c)。

本轮只复查在线内容，没有将当前测试仓库固定为本地提交。首次执行前由 A/B 保存采用的提交或内容哈希，不将旧阅读记录冒充已固定测试版本。

### G3：同一源码的双平台整体验收

负责人：C 提供平台，三人共同验收。

- [ ] 同一集成提交分别构建两架构，用户程序、内核和根镜像不混用机器码。
- [ ] 两平台都能启动 shell，并执行文件访问和用户程序。
- [ ] 两平台分别执行完整原版 usertests，保留慢速组及最终判定；其他要求的原版独立程序另列，不能把“69 项”自动等同于所有程序已执行。
- [ ] 两平台分别执行三文件系统与指定 VFS 测试；不拿 RISC-V 结果代替 LoongArch。
- [ ] 明确 CPU 数量、模拟机器、镜像和工具版本；单 CPU 启动不能声称多核完成。

判定：两个平台使用同一组公共功能；不接受一个只支持原生、另一个才支持新增后端的组合来代替统一目标。

## 3. 自测与联调定位责任

| 现象 | 先由谁定位 | 先查什么 |
|---|---|---|
| 找错后端、`/mnt/..` 异常、cwd/fd 泄漏 | A | 逐分量路径、挂载上下文、节点与实例引用 |
| 某格式内容错、截断后残留、空闲计数或簇链错 | B | 格式解析、块映射、目录更新、分配回收 |
| 同偏移读到其他盘内容、I/O 不返回、平台启动卡住 | C | dev 分发、请求状态、设备地址、中断与平台差异 |
| dup/fork 共享位置错、写入死锁 | A 主查，B/C 协助 | file 位置锁、后端锁、原生事务顺序和睡眠上下文 |
| 两平台一端成功另一端失败 | C 先查平台边界，A/B 复核公共代码假设 | 数据宽度/对齐、用户复制、异常帧、设备与构建产物 |
| 只在多人合并后失败 | A | 第一个失败集成提交、接口版本与变更范围 |

接口问题联合修复，不能仅按发生在哪个文件就推给某个人。先确定复现条件再改；不要通过屏蔽错误、删测例或回退功能制造“通过”。

| 测试范围 | 必要边界 | 负责人 |

| 格式支持与异常 | 不支持特性、超限名称/文件、短名限制、坏输入、空间不足、错误返回 | B |
| 数据完整性 | 零长度、跨块、跨簇、覆盖、较短截断、文件大小和所有字节一致 | B |

## 6. 合并节奏与完成标准

- 共享接口有变化时立即同步；每周至少安排两次简短接口/接入检查，具体时段由三人结合课表选择。检查只需对齐提交、接口变化、阻塞及下一次可验证交付，不要求长会议。
- 合并前模块负责人完成相关自测；A 在集成分支一次接一组相关改动，保存失败位置，避免同时合入平台大改和文件系统大改后无法定位。
- 日常改动运行受影响的定向检查；重要接入点运行原生回归；阶段和最终提交执行完整矩阵。测试通过后无新改动和新疑点不反复重跑。
- 集成分支已有失败时先复现修复或暂缓该模块接入，不在工作主线堆积未知失败。
- 最终相对 rev5 生成 diff，确认新增受控文件在内、未混入构建产物/凭据/大镜像，并在干净 rev5 上验证能还原成果。
- 本任务产生的分工讨论与记录存 `任务分配/`；同学日常开发证据按团队约定保存并在这里索引，不将所有无关任务的历史记录搬到本目录。
